## Architecture

Cross-platform app with a **Flutter frontend** and a **Rust backend**, bridged by **Flutter Rust Bridge (FRB)**. Flutter does UI only (Material 3); all business logic, persistence, and external API calls live in Rust.

```
lib/                Flutter UI (views/, widgets/, settings.dart, main.dart)
lib/src/rust/       FRB-GENERATED Dart — DO NOT edit by hand
rust/src/api/       Public surface exposed to Flutter (thin wrappers, one module per domain)
rust/src/handlers/  Business logic, coordinates repos + third_party. Created via `Handler::create`
rust/src/database/  SeaORM entities, repositories, enums; SQLite via `sea-orm`
rust/src/commands/  Plain data structs representing operations (input DTOs)
rust/src/models/    Output DTOs returned to Flutter
rust/src/third_party/  External APIs: OpenWeatherMap, Aviationstack, WorldTides, Unsplash, Overpass, Photon, Deutsche Bahn
rust/src/jobs/      Background jobs (weather sync, tidal sync, packing list updates) run via `run_background_jobs()`
rust/src/parsers/   Parsers (e.g. shared train data)
rust/migration/     Sea ORM migrations + paired `*_up.sql` / `*_down.sql` files
```

### Request flow (Flutter → Rust)
1. Flutter calls a generated function in `lib/src/rust/api/...`.
2. That hits a `pub async fn` in `rust/src/api/<domain>.rs`.
3. The API function acquires a handler via `DB.try_get::<XHandler>()` — `DB` is a process-wide `RwLock<Option<Database>>` initialized by `connect_db(path)` in `main.dart`.
4. The handler calls one or more `repositories::*` functions and returns a `models::*` type.

When adding a feature, follow this order: define `commands::*` input → add `repositories::*` method → write `handlers::*` logic → expose `pub async fn` in `api/<domain>.rs` → re-run codegen → consume the generated Dart API in `lib/views/`.

### FRB visibility rules
`rust/src/lib.rs` marks `database`, `logger`, `third_party`, `handlers`, `jobs`, `parsers` with `/// flutter_rust_bridge:ignore` — they are **not** exposed to Dart. Only `api`, `commands`, and `models` cross the bridge. If you add a new top-level module, decide explicitly whether Dart should see it.

### Database
- SQLite via SeaORM. Path is platform-specific (see `rust/src/database/mod.rs::storage`): Android uses a hardcoded app-data path, iOS uses the Flutter-provided documents path, desktop uses `./db.sqlite` (current working directory).
- `Migrator::up` runs automatically on `connect_db`. Add new migrations as a sibling module in `rust/migration/src/` and register them in `lib.rs`; pair each Rust migration file with `*_up.sql` / `*_down.sql`.

## Common commands

```bash
# Regenerate the FRB bridge after editing rust/src/api, commands, or models.
# Config is in flutter_rust_bridge.yaml (rust_input: crate::api, dart_output: lib/src/rust).
flutter_rust_bridge_codegen generate

# Flutter
flutter pub get
flutter analyze                       # lint (flutter_lints, see analysis_options.yaml)
flutter run                           # debug on default device
flutter build linux --release
flutter build macos --release
flutter build appbundle --release     # Android (Play Store)

# Rust (run from rust/)
cargo build
cargo test --workspace                # inline tests live in many src files
cargo test -p rust_lib_holiday_planner <test_name>   # single test
```

- `UNSPLASH_ACCESS_KEY`
- `OPENWEATHERMAP_API_KEY`
- `AVIATIONSTACK_API_KEY`
- `WORLD_TIDES_API_KEY`
- `GOOGLE_POLLEN_API_KEY`

## Conventions

- Always use braces on `if` statements.
- Don't add comments for obvious code; document only non-obvious *why*.
- Never edit `lib/src/rust/**` — it's regenerated by FRB codegen.
- `rust_lib_holiday_planner` is consumed by Flutter through the `rust_builder/` path dependency in `pubspec.yaml`; the cargokit setup there compiles Rust per-platform.

## Localization & translations

Flutter's `gen-l10n` with ARB files in `lib/l10n/`. Source locale is `app_en.arb`; additional locales (e.g. `app_de.arb`) mirror the same keys. Config lives in `l10n.yaml`. Never edit generated files.

- All user-facing strings must be defined in ARB files — no hardcoded strings in Dart.
- Every key has an `@key` metadata object with a `description` and, when applicable, `placeholders`.
- Placeholders must declare `type` and a string `example`. Use the `@key` object form, not the legacy `key@placeholders` form.
- Read strings with `AppLocalizations.of(context)!`.
- Declare supported locales in `MaterialApp.supportedLocales` and keep ARB files in sync.

Example ARB entry:

```json
"itemsCount": "{count} items",
"@itemsCount": {
  "description": "Label indicating how many items in a category",
  "placeholders": {
    "count": { "type": "int", "example": "5" }
  }
}
```

Usage: `Text(AppLocalizations.of(context)!.itemsCount(7))`.

Workflow to add a string: add the key + `@key` metadata to `app_en.arb`, mirror it in other locale ARBs, then `flutter gen-l10n` (or a build) regenerates the getters.
